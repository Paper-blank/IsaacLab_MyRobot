# 外骨骼 8 电机 `55AA` 控制通讯协议

## 1. 协议用途与边界

本文定义工控机向外骨骼电机控制器发送的 **8 电机同步目标帧**。每个电机占
6 字节，依次携带目标位置、**带方向的目标速度**和**非负加速度幅值/上限**。协议采用
固定帧长、大端字节序和逐字节异或校验。本文已经按接收固件的
`(high_byte << 8) | low_byte` 和角度/速度换算式更新；原“最大速度”名称不再表示
只能取正值的速度上限。

> **安全警告：** 本协议只规定数据如何编码，不能替代关节标定、机械/软件限位、
> 编码器反馈、通信看门狗、驱动器故障处理和硬件急停。仓库中的示例参数没有经过
> 实体机测量或安全认证，禁止直接用于通电或穿戴测试。

本协议当前只定义下行控制帧，不包含反馈帧、应答（ACK）、序号、时间戳、使能、
故障复位或急停命令。实体部署前，接收端必须有独立的通信超时保护；反馈和状态机
应按控制器手册另行定义。

## 2. 固定关节槽位

协议槽位不是 `ruleresult/v1` 数组的原始顺序。编码器必须按关节名称重排，禁止按
数组下标直接复制。

| 槽位 | 关节名称 | 机械语义 | 数据偏移 |
| ---: | --- | --- | ---: |
| 1 | `Lleg_to_Lfoot` | 左踝 | 3 |
| 2 | `Rleg_to_Rfoot` | 右踝 | 9 |
| 3 | `Lthigh_to_Lleg` | 左膝 | 15 |
| 4 | `Rthigh_to_Rleg` | 右膝 | 21 |
| 5 | `Lturn_to_Lthigh` | 左髋屈伸 | 27 |
| 6 | `Rturn_to_Rthigh` | 右髋屈伸 | 33 |
| 7 | `base_to_Lturn` | 左髋转向 | 39 |
| 8 | `base_to_Rturn` | 右髋转向 | 45 |

“数据偏移”是该槽位目标位置**高字节**在完整帧中的零基字节下标。

## 3. 完整帧结构

一帧固定为 53 字节：

```text
帧头 2 B + 长度 1 B + 电机数据 48 B + 校验 1 B + 帧尾 1 B = 53 B
```

| 字节偏移 | 长度 | 字段 | 固定值/说明 |
| ---: | ---: | --- | --- |
| 0 | 1 B | 帧头 1 | `0x55` |
| 1 | 1 B | 帧头 2 | `0xAA` |
| 2 | 1 B | 长度 | `0x32` |
| 3--50 | 48 B | 电机数据 | 8 个槽位，每槽 6 B |
| 51 | 1 B | XOR 校验 | 对偏移 0--50 的字节逐字节异或 |
| 52 | 1 B | 帧尾 | `0x5A` |

长度字段 `0x32` 等于十进制 50，表示长度字段之后的 50 字节，即：

```text
48 B 电机数据 + 1 B 校验 + 1 B 帧尾 = 50 B = 0x32
```

因此，`0x32` 不是整帧长度，也不是仅数据区长度。接收端应同时检查长度字段为
`0x32` 且实际帧长为 53 字节。

## 4. 单个电机的数据结构

每个槽位固定为 6 字节：

| 槽内偏移 | 长度 | 类型 | 字段 | 数值范围 |
| ---: | ---: | --- | --- | ---: |
| 0 | 2 B | `uint16` | 目标位置 | 原始值 `0..65535`，对应 `-12.57..+12.57 rad` |
| 2 | 2 B | `uint16` | 目标速度（带方向） | 原始值 `0..65535`，对应 `-20..+20 rad/s` |
| 4 | 2 B | `uint16` | 加速度幅值/上限（不带方向） | 原始值 `0..65535`，对应 `0..65.535 rad/s²` |

**通俗解释：** 无符号整数（unsigned integer）只是线路上保存数字的方法，不等于
对应的物理量一定非负。角度和速度的原始值先做比例缩放、再减去中点，因此可以表示
负方向；加速度字段没有中点偏移，只能表示幅值或限制，不能保留正负方向。

**技术细节：** 所有 16 位整数均使用**大端序（big-endian）**，即高字节在前。例如
`0x1234` 在线路上的两个字节为：

```text
12 34
```

各槽位的完整偏移如下：

| 槽位 | 目标位置 | 目标速度 | 加速度幅值/上限 |
| ---: | --- | --- | --- |
| 1 | 3--4 | 5--6 | 7--8 |
| 2 | 9--10 | 11--12 | 13--14 |
| 3 | 15--16 | 17--18 | 19--20 |
| 4 | 21--22 | 23--24 | 25--26 |
| 5 | 27--28 | 29--30 | 31--32 |
| 6 | 33--34 | 35--36 | 37--38 |
| 7 | 39--40 | 41--42 | 43--44 |
| 8 | 45--46 | 47--48 | 49--50 |

## 5. 浮点物理量到 `uint16` 的转换

### 5.1 先做关节到电机侧标定：只转换一次

**通俗解释：** 仿真关节角度不一定是驱动器眼中的电机角度；左右侧可能镜像，零位和
减速比也可能不同。先把它们翻译成驱动器坐标，再编码。不能在映射层和协议层各乘一次
减速比，也不能把协议量程当作人体能够安全运动的范围。

**技术细节：** `ruleresult/v1` 使用仿真关节单位：位置为 `rad`、速度为 `rad/s`、角加速度为
`rad/s^2`。编码前先按每个关节的实测标定转换到电机侧：

```text
q_motor = zero_offset_rad + direction * gear_ratio * q_joint
v_motor =                   direction * gear_ratio * v_joint
a_motor_magnitude = abs(direction * gear_ratio * a_joint)
```

其中 `direction` 只能是 `+1` 或 `-1`，`gear_ratio` 必须大于零。速度必须保留符号，
不能取 `abs(v_joint)`；只有加速度字段取幅值。如果固件协议中的 `rad` 已是关节输出轴
单位，应按该定义标定，不要再乘电机传动比。数值超限、NaN、Inf 都必须拒绝生成帧。

协议表示范围与机械安全限位是两层约束：`±12.57 rad` 是**编码范围**，不是踝、膝、髋
或人体的安全活动范围。每个电机仍必须有更保守的实测软限位和速度/加速度安全上限。

### 5.2 目标位置：固定 `-12.57..+12.57 rad`

**通俗解释：** 把 `-12.57 rad` 到 `+12.57 rad` 平均分成 65535 个间隔，原始值 0 表示
最小角度，65535 表示最大角度。每个关节的软件软限位只负责检查是否允许发送，不能
改变这把“量尺”，否则接收端会得到错误角度。

**技术细节：** 发送端严格使用接收固件给出的固定换算：

```text
position_u16 = round_half_up((q_motor + 12.57) / 25.14 * 65535)
q_motor     = position_u16 / 65535 * 25.14 - 12.57
```

配置中的 `position_min_rad`、`position_max_rad` 保留字段名，但含义是电机侧**软件
安全范围**，必须位于协议硬范围 `[-12.57, +12.57]` 内，且最小值小于最大值。它们
不再参与量化比例计算。位置超出这两层范围时应拒绝编码，不允许静默截断。

### 5.3 目标速度：固定 `-20..+20 rad/s`，必须保留方向

**通俗解释：** 原始值小于中点表示负方向，大于中点表示正方向。把一个负速度取绝对值
再编码，会让接收端朝相反方向运动；发送一个很小的原始整数，也不代表低速，而接近
`-20 rad/s`。

**技术细节：** 速度按用户提供的固件公式编码/解码：

```text
velocity_u16 = round_half_up((v_motor + 20.0) / 40.0 * 65535)
v_motor      = velocity_u16 / 65535 * 40.0 - 20.0
```

`velocity_full_scale_rad_s` 固定为 `20.0`，不是可调编码参数；安全上限
`command_max_velocity_rad_s` 对 `abs(v_motor)` 检查。如果源码原始结构还使用
`RawMotorCommand.max_speed` 字段名，这只是兼容旧 API 的名称，含义已是**目标速度的
原始编码值**；新语义访问名为 `target_velocity`，不可当作非负速度限值。

### 5.4 加速度：固定 `0..65.535 rad/s²`，分辨率 `0.001 rad/s²`

**通俗解释：** 加速度字段只有“大小”，没有“方向”。例如规划导数 `-2 rad/s²` 可以
转换成幅值 `2 rad/s²` 或受审核的加速度上限，但不能把负号藏进这个无符号字段。

**技术细节：** 根据用户给出的范围，本文补齐以下线性换算约定：

```text
accel_u16 = round_half_up(a_command_rad_s2 * 1000)
a_command_rad_s2 = accel_u16 / 1000.0
```

用户目前给出的 C 代码只有角度、速度解析；**加速度除以 1000 的固件实现仍需现场
确认**，不能假设已经支持。`acceleration_full_scale_rad_s2` 必须是 `65.535`。

本项目的 `limit_source` 只选择加速度字段的来源，**不改变速度来源**：

- `trajectory`（默认）：发送 `abs(gear_ratio * a_joint)`；速度仍发送
  `direction * gear_ratio * v_joint`。只有在导数质量、插值方式和时间戳已验证后使用。
- `configured`：发送审核过的固定 `command_max_acceleration_rad_s2` 加速度上限，
  速度仍来自带符号轨迹，不发送固定速度。

`configured` 必须填写 `command_max_velocity_rad_s` 和
`command_max_acceleration_rad_s2`；`trajectory` 可选填写，两者都用于检查实际轨迹的
速度/加速度**幅值**，超过上限时拒绝编码，即使 `configured` 最终发送固定加速度也
不能跳过原始导数检查。未填写时只使用协议硬范围，不能据此认为实体已经安全。
配置值不得超过 `20.0 rad/s` 和 `65.535 rad/s²`。限幅/时间缩放应由安全规划层完成，
编码器本身拒绝非法值，不隐式裁剪或改变轨迹。

### 5.5 Python 编码示例与零点量化

```python
import math
import struct

def quantize_motor(q_rad, v_rad_s, a_magnitude_rad_s2):
    values = (q_rad, v_rad_s, a_magnitude_rad_s2)
    if not all(math.isfinite(x) for x in values):
        raise ValueError("non-finite target")
    if not (-12.57 <= q_rad <= 12.57 and -20.0 <= v_rad_s <= 20.0):
        raise ValueError("position/velocity outside protocol range")
    if not 0.0 <= a_magnitude_rad_s2 <= 65.535:
        raise ValueError("acceleration outside protocol range")
    q_u16 = math.floor((q_rad + 12.57) / 25.14 * 65535 + 0.5)
    v_u16 = math.floor((v_rad_s + 20.0) / 40.0 * 65535 + 0.5)
    a_u16 = math.floor(a_magnitude_rad_s2 * 1000.0 + 0.5)
    return struct.pack(">HHH", q_u16, v_u16, a_u16)  # 高字节在前

# 仅演示硬量程量化；实体应用必须在量化前及反解后都验证软限位，见5.6。
assert quantize_motor(0.0, 0.0, 0.0) == bytes.fromhex("80 00 80 00 00 00")
```

`round_half_up` 表示恰好在半整数时向上取整；Python `round()` 的银行家舍入不是本约定。
因为 65535 为奇数，角度/速度的物理零点对应原始值 `32767.5`，没有精确零编码。
按上述规则零点发送 `0x8000`，解码约为 `+0.000191806 rad` 与
`+0.000305180 rad/s`；采用 `0x7FFF` 则为相同幅值的负值。真实停止应由经验证的控制器
保持/停车逻辑负责，不能依赖清零数据或本协议的微小非零速度。

角度、速度的最小步距分别约为 `0.000383612 rad` 和 `0.000610361 rad/s`；实际安全检查
应考虑量化后的接收目标。协议只规定字段语义，不能据此推断驱动器已经支持位置+速度
前馈，也不能把加速度直接当力矩；控制模式必须按固件手册确认。

### 5.6 量化后也必须检查：不安全就拒绝，不裁剪

**通俗解释：** 浮点目标刚好在安全边界内，四舍五入成整数后可能“跨过边界”。因此
不能只检查发送前的浮点数；还要按接收端公式把整数还原，确认电机真正看到的目标
也安全。检查失败就不生成帧，不能偷偷改小数值或放宽限位。

**技术细节：** 生产编码器先检查标定后的原始 `q/v/a`，再量化、反解三个字段，并再次
检查电机侧 `position_min/max_rad`、速度幅值上限和加速度上限；任一失败即拒绝编码
（fail-closed）。例如，`q=0` 而软上限为 `0`，反解约 `+0.000191806 rad` 后会被拒绝；
加速度 `2.0006 rad/s²` 在同值上限内，但编码后反解为 `2.001 rad/s²`，也会被拒绝。
将 `command_max_velocity_rad_s` 设为 `0` **不是停车命令**：连零速度目标也无法精确
编码，反解后的微小非零速度会超过零上限，因此编码失败；停车应走独立安全状态机。

规划轨迹应为量化和浮点运算预留安全余量（margin），不要贴着软限位或命令上限
取值。角度/速度最小步距见5.5，加速度步距为 `0.001 rad/s²`；边界余量至少考虑
半个量化步距，再加现场浮点和测量误差，并经安全评审确认，而不是扩大已审核限位。
Python 一般按 64 位浮点计算（double），示例固件按 32 位浮点（float）计算，
最低有效位（unit in the last place，ULP）和计算舍入可能不同；不能认为 Python
通过检查就保证固件结果相同。接收端必须对**实际解析后的值**重复安全范围、故障和
急停检查，失败时不提交任何电机目标。

## 6. XOR 校验

校验按**原始字节**逐字节异或，不是对字符串 `"55AA"` 的字符做异或：

```python
# 仅用于断能校验测试；全零数据不代表停车，不能发给使能电机。
prefix = bytes.fromhex("55 AA 32") + bytes(48)
checksum = 0
for byte in prefix:           # 偏移 0..50，包含帧头、长度和全部数据
    checksum ^= byte
assert checksum == 0xCD
frame = prefix + bytes((checksum, 0x5A))
assert len(frame) == 53
```

校验范围包括：

- 帧头 `0x55 0xAA`；
- 长度 `0x32`；
- 48 字节电机数据。

校验范围不包括校验字节自身，也不包括帧尾 `0x5A`。例如，当 48 字节数据全为零时：

```text
checksum = 0x55 XOR 0xAA XOR 0x32 = 0xCD
```

对应帧的开头和结尾为：

```text
55 AA 32 [48 个 00] CD 5A
```

**重要：全零数据帧不是静止命令。** 每个电机实际解码为 `q=-12.57 rad`、
`v=-20 rad/s`、`a=0 rad/s²`。这个向量只能用于断能协议测试，不可向使能设备发送。

## 7. 发送与接收规则

发送端每个控制周期应一次生成一帧完整的 8 电机命令，不能把左右腿拆成不同周期。
接收端建议按以下顺序处理：

1. 在字节流中查找连续帧头 `55 AA`。
2. 读取长度并确认等于 `0x32`。
3. 等待缓冲区具备完整 53 字节，不完整时继续接收而不是提前解析。
4. 检查帧尾为 `0x5A`。
5. 重新计算偏移 0--50 的 XOR，并与偏移 51 比较。
6. 校验通过后，一次性提交全部 8 个电机目标。
7. 任一步失败都丢弃该候选帧并重新同步帧头，不执行其中的部分电机数据。

本帧没有序号和时间戳，不能自行检测重复帧或乱序帧。控制器必须配置接收看门狗：
在经过评审的超时时间内没有收到合法完整帧时，进入预先定义的 HOLD、卸力或安全停机
状态，禁止无限保持最后一帧继续运动。

### 7.1 接收固件 C 解析示例

下面的代码先验证整帧，再暂存 8 个电机目标。`uartReceive` 指向**48 字节数据区的
第一个字节**，不是完整帧头；因此槽位 `i=1..8` 的数据偏移是 `6*(i-1)`。
如果直接索引完整帧 `frame`，则还需要加 3。

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    float angle_rad;
    float velocity_rad_s;
    float acceleration_magnitude_rad_s2;
} MotorTarget;

static uint16_t read_u16_be(const uint8_t *p) {
    return (uint16_t)(((uint16_t)p[0] << 8) | (uint16_t)p[1]);
}

bool decode_55aa(const uint8_t *frame, size_t size, MotorTarget targets[8]) {
    if (frame == NULL || targets == NULL || size != 53) return false;
    if (frame[0] != 0x55 || frame[1] != 0xAA || frame[2] != 0x32) return false;
    if (frame[52] != 0x5A) return false;
    uint8_t checksum = 0;
    for (size_t j = 0; j < 51; ++j) checksum ^= frame[j];
    if (checksum != frame[51]) return false;

    const uint8_t *uartReceive = frame + 3;
    for (size_t i = 1; i <= 8; ++i) {
        const uint8_t *p = uartReceive + (i - 1) * 6;
        targets[i - 1].angle_rad = ((float)read_u16_be(p) / 65535.0f) * 25.14f - 12.57f;
        targets[i - 1].velocity_rad_s = ((float)read_u16_be(p + 2) / 65535.0f) * 40.0f - 20.0f;
        targets[i - 1].acceleration_magnitude_rad_s2 = (float)read_u16_be(p + 4) / 1000.0f;
    }
    return true;  /* 调用方：先检查全部软限位、模式、故障、急停，再原子提交8电机 */
}
```

这不是完整实体固件：驱动器应对解码后的每个目标再次做关节专属安全检查，并将整组
目标暂存、在同一控制周期锁存；不能在 `for` 循环中边解析边使电机运动。加速度语义
和缩放须与固件负责人核对，看门狗和急停必须在独立路径上工作。

## 8. 传输介质注意事项

- **串口**：53 字节可作为连续字节流发送；必须实现拆包、粘包和重新同步处理。
- **CAN FD**：数据长度码（Data Length Code，DLC）不能直接表示 53 B，必须使用
  对应 64 B 的 DLC（编码 `15/0xF`），在 53 B 协议帧后加入 11 B 双方约定的填充。
  传输适配层接收后去除这 11 B，再把前 53 B 交给本协议解码器；固定帧解码器不接受
  64 B。填充不属于本协议，不改变 `0x32`，不参与协议 XOR。CAN ID、FD/BRS 配置和
  接收超时仍需另行确定。
- **经典 CAN**：单帧只有 8 字节，不能直接承载本协议完整帧；必须定义分片、序号、
  重组和超时规则，或改用 CAN FD。本文没有定义经典 CAN 分片协议。
- **EtherCAT**：可把 53 字节映射到一个输出区，但仍需由主站保证周期同步和看门狗。

策略名义周期为 20 ms（50 Hz），不表示任何传输介质天然满足 50 Hz 实时性。工控机
必须使用单调时钟、绝对 deadline 和实测的最坏发送时间。
串口若使用 8N1，每字节占 10 个线路位；50 Hz × 53 B × 10 bit = 26.5 kbit/s，
建议从至少 115200 baud 做延迟实测，仍需预留反馈和处理时间。

## 9. 配置文件

示例模板位于：

```text
scripts/deployment/protocol_55aa_config.example.json
```

其 schema 为 `exoskeleton-55aa-config/v2`，`byte_order` 必须为 `big`，
`velocity_full_scale_rad_s` 必须为 `20.0`，`acceleration_full_scale_rad_s2` 必须为
`65.535`。包含固定槽位、电机侧位置软限位、零位、方向、减速比和命令安全上限。
`slot` 必须是 JSON 整数 `1..8`，`direction` 必须是 JSON 整数 `1` 或 `-1`：不能写
`true`、`false`、`1.0` 或字符串 `"1"`，加载器不会把布尔/浮点/字符串偷偷转成整数。
模板中的 `example_only: true` 会让协议加载器
**主动拒绝加载和编码**，因此模板本身故意不能生成输出帧。

启用一份现场配置必须完成以下全部步骤：复制模板到新的现场配置文件；逐项替换 8 个
电机的全部实测参数；完成双人复核、断能和 HIL 测试；最后才把副本中的
`example_only` 改为 `false`。不要直接修改或覆盖示例模板，也不要只改布尔标志而沿用
示例数字。该加载检查只是防误用措施，不代表参数已经安全认证。

### 9.1 从旧 `v1` 配置迁移

旧 `v1` 配置采用小端、按每电机位置范围量化、非负速度上限，与本次固件定义不兼容。
加载器拒绝 `v1`，不自动猜测或兼容旧格式。迁移应重新复制 `v2` 模板，复核所有软限位
与标定，固定大端和上述满量程，并确认速度带方向、加速度不带方向。不能只替换
`schema` 字符串后沿用旧含义。

旧 `.bin` 文件在线路上没有版本字段，而且旧、新帧长度和 XOR 都相同；接收端无法
仅靠校验识别旧帧。必须把旧文件隔离、明确标记禁止播放，并从可溯源的浮点 JSONL
重新导出到**全新的输出路径**。不要把旧小端帧和新大端帧追加到同一个文件。模型
checkpoint 和 `ruleresult/v1` 浮点 JSONL 不受这次线路协议变化影响。

记录器新打开协议输出时会拒绝已有的**非空** `.bin`，原文件不会被修改；已有空文件
允许使用。同一次运行中的各控制周期仍追加 53 字节；跨运行请指定新路径并做好
外部版本/采样周期记录，不能通过删除检查或继续旧文件来绕过防混写保护。
